## 3. 三个必须写下来的缺口

### 缺口 1 · 弹题只"暂停"不"作答"

- **现状**：Autovisor 在课中弹题时**暂停播放并等待**；OCS **随机选一个选项**提交。
- **后果**：自动跑课时，弹题会成为**必然的阻塞点**（等不到人点就一直停），
  而随机作答会**污染掌握度数据**。
- **本项目的做法**：把弹题做成一条完整的 Agent 链路（对应目标 3）

```
弹窗出现 → 读 DOM 取出题干+选项 → 生成待答工单(answer_broker)
        → 操控 Agent/LLM 作答 → 回填 → 注入 DOM 点击 → 关闭弹窗 → 继续播放
        → 超时未答 → 按策略处理（默认：暂停转人工，绝不随机作答）
```

> **关键取舍：超时默认不随机作答。** OCS 的随机选会在掌握度/练习里留下错答记录，
> 而"暂停转人工"最坏只是慢。宁可慢，不可错。

### 缺口 2 · 任务点类型拿不到结构化出口

- **现状**：上游都是"跑完整课"，没有"列出任务点及其类型/状态"的接口。
- **后果**：`run_video_tasks` / `run_reading_tasks` 的类型过滤无从下手。
- **本项目的做法**：由统一层自建 `scan_tasks`（C09），从页面 DOM 直接读。
  各布局的已完成标记已在 01 §2.1 摸清；**读不到时明确降级并写进 `warnings`**，
  绝不静默跑整章。

### 缺口 3 · 新形态课程（`ai-smart-course-student-pro`）只能只读

- **原因**：`zhihuishu-resource-helper` **无许可证**，不能复制其写入逻辑；
  自行实现写操作风险高（该页面是"逐个打开+刷新接续"的脆弱流程）。
- **本项目的做法**：该域只做**只读盘点**（列资源、读进度）；
  写操作如实标 `partial` 并在 `next_actions` 里建议人工。

## 4. 与两个姊妹项目的接口一致性

三个平台**共用**：能力编号（C01–C51）、Envelope 字段、8 态状态机、8 类错误分类、
29 条命令名、`adapters`/`probe`/`status` 等控制命令。

**只在这三处不同**（都是平台客观差异，不是设计差异）：

| 维度 | cx | zhihui | zhihuishu |
|---|---|---|---|
| `Course.course_id` 语义 | 数字课程号 | courseId | 智慧树 `recruitId`/`courseId` |
| 登录凭据形态 | 账密 AES / cookie | SSO Token | cookie + 滑块 |
| `adapter` 取值 | `chaoxing-cli` 等 | `icve_toolkit` 等 | `zhs-autovisor` / `zhs-browser` |
